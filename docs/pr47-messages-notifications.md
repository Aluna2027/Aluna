# Path 2: Messages and Notifications

Blocks are directional actor pairs. Organization admins act for their organization, so its block applies to that organization's conversations and is visible to its admins; ordinary members cannot manage it. Blocking prevents new incoming messages and their notification trigger. It does not delete history or suppress unrelated notifications. Outgoing messages are permitted unless the recipient has blocked that sender. Unblock only affects future sends. A database BEFORE INSERT guard covers server actions and direct API inserts, validates sender ownership/participation, and locks the conversation against concurrent controls. Existing read authorization remains unchanged.

Delete conversation is a confirmed per-profile hide, including for organization administrators sharing an inbox. Other participants/admins keep their history. A successfully accepted new message restores hidden inbox entries; failed/blocked sends do not. Conversation row locks serialize hide/send, and hidden entries are filtered before the inbox limit. Refresh and stale links do not restore hidden entries. No shared conversation or message DELETE is used.

Notifications default to New (unread); History shows read rows. Opening either tab does not mark rows read. View submits the selected ID, updates through existing recipient/post RLS, checks success and navigates to an allowlisted local destination. Existing kinds and comment-parent navigation are preserved. Existing shared counters refresh on destination navigation/Realtime/focus; layout revalidation follows the update. Member-post privacy remains enforced by existing RLS.
